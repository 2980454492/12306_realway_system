## 审查流程

1. **逐文件审查 git diff** — 按下方清单逐项检查每个变更文件的注释
2. **同文件一致性扫描** — 打开有新增/修改函数的文件，从上到下扫一遍：
   - 所有 `/** */` 风格一致（长度、语气、有无 @param）
   - 段落分隔符 `// ──` 数量适中（~5 个函数一组）
   - 不存在"前 3 个函数有详细注释，后 5 个只有函数名"的断层

## 审查清单

### 底线项（缺了就是未完成）

- [ ] 新增文件有文件头：`// filename.xxx — 一句话职责`
- [ ] 新增函数/方法有注释：`/** 做什么 */`，一行说清
- [ ] 新增 HTTP API 端点有注释：`/** METHOD /path — 做什么 */`
- [ ] 新增类/结构体有注释：代表什么实体、被谁使用
- [ ] 新增常量有注释：`/** 含义 */`，有"为什么是这个值"时才多写
- [ ] 关键设计决策旁有"为什么"注释

### 格式统一（同文件内一刀切）

> 打开文件，从第一个函数扫到最后一个，注释格式必须一致。不允许混用。

| 元素 | 格式 | 示例 |
|------|------|------|
| 文件头 | `// file.xxx — 一句话职责` | `// utils.h — 全局工具函数` |
| C++ 公开函数 | `/** 做什么 */`（单独一行，在函数上方） | `/** 两站点间的大圆距离（km），Haversine 公式 */` |
| HTTP API 端点 | `/** METHOD /path — 做什么 */`（在 `app.Get/Post/Put/Delete` 紧上方） | `/** POST /api/admin/lines — 新增线路 */` |
| C++ 内部函数 | `// 做什么` | `// 从索引加载，失败回退到全量构建` |
| 常量 | `/** 含义 */` | `/** 二等座每公里基准费率（元） */` |
| 段落分隔 | `// ── 段落名 ──` | `// ── 时间工具 ──` |
| 行内"为什么" | `// 原因` | `int margin = 5;  // 运行图安全裕量(分钟)` |

### 具体禁止

- ❌ 函数签名末尾挂 `// 行内注释`（如 `bool isFuture(..., int hhmm = 0) {  // 注释`）→ 放入 `/** */` 内
- ❌ 同一文件内 `/** */` 和 `//` 混用来注释同级别的函数
- ❌ 多行 `/** ... */` 和单行 `/** */` 混用（统一单行）
- ❌ `@param` 出现在简单工具函数中（个别复杂函数除外）
- ❌ 注释掉的代码块
- ❌ 函数体内的 `/* */`
- ❌ "TODO 以后改"

## 输出格式

只报问题，不报通过项。按关注度排序：

| 级别 | 含义 | 示例 |
|------|------|------|
| 🔴 缺失 | 底线项不满足 | 新文件缺文件头、新函数无注释 |
| 🟡 不一致 | 同文件内注释风格混用 | 前半段 `/** */`，后半段 `//` |
| 🔵 冗余 | 废话 / 过期 / 无价值 | 修改代码未更新注释、纯复述代码 |

每个问题附：**文件:行号** + **问题描述** + **修复建议（一句话）**。
